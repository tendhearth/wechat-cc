这次交付的边界

四个核心画面及其可点击流程，中英文、浅深色、离线和已处理状态。它用于评审设计，不连接电脑，不发送真实请求，不创建 Expo 工程，也没有完成双平台真机推送验收。

1 / 导航与主线

底部固定「此刻 / 一起做」。此刻聚焦需要决定的事及 CC 的简短近况；一起做承载聊天、任务和产出。设置通过右上角头像进入。输入入口始终容易找到，进入事项后变为「接着跟 CC 说一句」。

画面用户看到什么主要操作
01 此刻需要决定的请求放在角色与动态之前。CC 的话只占一两句。活动按事情组织。查看上下文；跟 CC 说一句；进入事项。
02 交办自然语言输入、图片入口、可展开的项目与执行者设置。默认沿用合理上下文。发送；保留草稿；调整项目。
03 进展CC 对当前进展的概括、已发生的步骤、待决定事项。按需展开代码改动与执行信息。批准前查看；继续交流；检查成果。
04 批准动作、目的、作用范围和影响。完整请求上下文与具体操作并存。允许这一步或先不做；已处理时返回事项。

示例情境：整理作品集的手机首页。CC 完成布局调整，需要安装图片处理组件 sharp；用户查看下载、安装脚本和依赖更新的影响后决定。该操作仅为原型演示。

状态使用「正在整理 / 等你决定 / 这一轮已回复 / 事情完成」。不用虚构百分比，不将工具返回或本轮答完等同整件事完成。

2 / 视觉与 CC

  • 按用户确认，以桌面作为颜色基准：浅色底 #faf8f3、卡片 #fffdf9、木棕正文 #493e32、辅助文字 #796f63、边线 #e4ddd2，直接沿用桌面 cc-life.css / cc-surfaces.css；主按钮采用事项页 #58654c，导航选中采用桌面 #f7ead2 / #674c2d。大面积灰绿色已移除。深色以暖炭黑 #221f1b、暖灰卡片 #2c2823 和象牙文字 #f1e9dc 延展；桌面尚无深色界面，这部分是手机设计的同色系延展。明暗是外观选择，不表示在线或离线。
  • 角色保留 C 形尾巴、竖条眼睛、安静而有分量的身体。原型直接复用桌面与现有手机版共同使用、已经验收的 canonical/lit/front.png 与 canonical/unlit/front.png，不再重画角色。静态素材保持原始像素；动效留待使用同一资产体系时设计。
  • 角色回应以尾巴角度、轻微姿态为主。所有工作状态同时有文字；减少动态设置下禁用动作。失败和离线不用责备或失落表情向用户施压。
  • 批准卡片是阅读焦点。装饰不抢占上下文，批准与拒绝都能直接找到。

3 / 状态约定

情形界面行为
电脑离线显示上次同步记录；仍可写草稿。发送、批准、拒绝均不可提交。重连后重新拉取状态；草稿由用户主动发送。
另一端已经处理保留请求上下文，显示已处理，移除可提交按钮。提供返回事项入口。
重复点击提交期间锁定操作；服务端的请求身份和最终结果决定状态，避免仅用客户端乐观成功。
收到旧通知先定位事项并拉最新详情，再展示当前请求。没有待处理请求则显示已处理或最新事项状态。
同事项有多个请求展示待处理请求列表让用户选。现有通知不能可靠定位其中某一个请求。
设备撤销或配对失效停止提交，提示重新配对；清理可用密钥和令牌。与暂时离线分开表达。
通知解密失败或超时保留中性提示，打开应用后重新同步。通知不直接执行允许操作。

原型中的离线、已处理、通知均是手动切换的演示状态；正式客户端须由真实连接状态和最新 API 响应驱动。

4 / 已有接口与接入缺口

基线为本地远端引用 origin/dev@6527ba2f，不是当前检出的旧 master。没有修改任何仓库分支或共享服务。

已有事实原生客户端需要完成
@wechat-cc/protocol：纯 TypeScript、noble、zod；请求、订阅、加密和推送向量。React Native WebSocket 适配；Hermes 中随机数、TextEncoder/Decoder、BigInt 与 DataView 验证；按 API schema 解析业务响应。
订阅发送摘要/版本号。收到变化后拉取详情、重连补同步、处理多设备同时操作。
通知业务载荷为 ts/kind/title/body/taskId?。冷启动后调用 GET /m/api/matter?id=…，从最新详情选定请求。不能由 taskId 推断唯一批准项。
批准请求需要 id/runId/requestId/decision。提交准确身份；覆盖已失效、重复提交、断网和设备撤销。
APNs：中性 alert、mutable-content、密文。FCM：HIGH priority、data-only 密文。Swift 通知扩展与 Kotlin messaging service、安全密钥访问、后台展示、平台通知外观。
POST /m/api/push/register 接受设备的 platform/token。通知权限状态、推送 token 获取和刷新、重装后的恢复。
手机端尚无完整代码 diff 路由。补路由及对应鉴权登记。当前原型中 diff 明确标为示例，不承诺接口已完成。
需要处理的通知时间窗口

APNs/FCM 的 TTL 为 1 小时，openPush 接受前后 10 分钟的时间窗口。迟到消息可能无法显示解密正文。正式验收必须覆盖中性提示与打开刷新；时间窗口是否调整应由协议维护者决定，不能由 UI 层绕过。

5 / 原生验证准备与顺序

当前机器有 xcrun 及 iOS 26.5 / 27.0 模拟器运行时。PATH 与标准 Android SDK 路径未找到 adb，因此尚未确认 Android 设备连通。没有读取凭据、安装 App 或发送推送。

  1. 对齐固定向量：Swift / Kotlin 分别通过已有 push.json，覆盖正常内容、错密钥、篡改、过期与未来时间。
  2. 验证密钥边界：配对后保存设备令牌和派生推送密钥；验证 App 与 iOS 扩展能按预定锁屏策略访问，撤销后清理。
  3. 登记推送令牌：覆盖首次授权、拒绝授权、token 刷新与重新安装。
  4. 真机收取：在前台、后台和进程不运行时验证 APNs / FCM 展示；覆盖解密失败、延迟和扩展超时。
  5. 冷启动定位：点通知进入事项，拉新状态，分别处理单条、多条、已处理和已失效请求。
  6. 完成一次批准：手机提交后观察电脑实际行为与两端状态更新，覆盖断网和重复点击。

模拟器与浏览器预览只能用于界面和部分链路检查，不能替代 iPhone/Android 的真实后台通知验收。
