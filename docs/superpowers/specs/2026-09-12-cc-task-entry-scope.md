# CC「一起做」：先成为可靠的 Claude / Codex 任务入口

日期：2026-09-12。状态：用户已确认产品方向；本文记录调研结论、收敛后的范围和待实现的验收标准，不表示功能已完成。

## 这一阶段只回答一个问题

用户能否在 CC 里完成日常 Claude Code / Codex 任务，而不必频繁回到各自 CLI？

从 CC 发起、接着做、处理权限、查看执行过程、停止任务、检查成果，都应在同一处完成。能同时照看不同项目，是这个目标的一部分。多模型自动编排、职业工作台、流程编辑器和跨设备迁移暂不扩展。

「此刻」和 CC 自己的生活保持现有边界。「一起做」采用更专业、直接的工作界面。陪伴体现在记得任务、接得上、需要用户时及时出现，不靠每一步追加一段 CC 总结。

本文调整 2026-09-11 工作台设计的后续目标：单一全局执行锁和常驻三栏属于已有版本，不再作为最终产品约束。未在此变更的数据访问、成果快照、微信显式续接和冻结美术约束继续有效。

这三者的启发不需要变成三套面板。CC 保留一个工作入口，逐项验证并接入真正需要的能力。

## 默认界面

两栏：左侧项目与任务，右侧当前任务完整对话。

- 左栏按项目收纳任务，显示短标题、执行者、真实状态和是否需要用户。历史可搜索。创建时只需选文件夹、交代事情；执行者沿用上次选择，允许直接改。
- 主区连续展示用户要求和执行者回复，正在进行的操作用简短状态呈现。原始输出可展开；不能只展示最后一条摘要，把此前所有对话藏起来。
- 文件、差异和具体执行记录按需打开，关闭后回到原来的对话位置。主区不常驻第三栏。
- 输入继续发给本任务绑定的原执行会话。任务执行中如何补充，必须由适配器确认是即时传达还是排队；页面明确标识，不能默默启动另一个会话。
- 子 agent 默认收在对应执行步骤下面。只有确有来源事件时才显示数量与状态；不能根据文本猜一棵执行树。需要用户处理的阻塞必须浮到主任务。
- 后续增加一个明确动作“交给 Claude / Codex 检查”。交接记录保留来源、要求和成果版本；不用用户先画流程，也不在两个执行者之间无限自动互发。

配色沿用 CC 的暖纸色、清晰深色文字和克制图标；工作区减少大插画和装饰性空白。任务列表里的 Claude / Codex 表示执行者，不与 API 厂商、模型名称和连接协议混排。

## CC 管理什么

CC 负责组织项目、维持会话、登记执行状态、递送请求、呈现成果。普通消息无需再让 CC 调一次模型改写；用户能直接读到执行者的回答，并分辨哪段是 CC 的协调说明。

一个 CC 任务可以关联多个执行者会话，但每个会话有自己的身份和历史。“请另一个检查”是新建或续接明确的接收方会话，不是给原历史换一个模型标签。

不同项目的会话、草稿、成果和权限请求必须隔离。同一目录存在两个写入任务时，先处理目录占用或明确创建隔离工作副本；会话隔离不等于文件隔离。普通文件夹也必须可用，不强制用户先学 Git。

## 接入边界

优先使用执行工具支持的会话与事件接口。终端视图可用于诊断，但主体验不靠抓屏幕文字或模拟键盘拼接状态。

首次连接应识别已安装工具及可用配置，不擅自覆盖用户原配置。不把 API 调用假装成已安装 Claude Code / Codex 的同等执行环境。模型、权限、工作目录、工具配置是否一致必须实测。

三件事分别验收：

1. 从 CC 新建并续接任务。
2. 读取已有 CLI 历史，在支持的条件下恢复同一原生会话。
3. 接管正在其他程序里运行的会话。

第 3 件不属于当前承诺。能够读取历史不表示能够控制原进程。恢复时须避免两个控制端同时写同一会话；不支持恢复就说明原因，用户可以选择带本任务上下文新开，而不能显示“已接管”。保留原生会话 ID，也不等于保证另一款桌面 App 自动显示 CC 发起的全部记录。

## 本地实现差距

以下是收敛范围时（`73287509`）的基线，依据当时的 `src/core/workbench/service.ts`、`store.ts`、`agent-provider.ts`、`codex-agent-provider.ts` 和 `apps/desktop/src/modules/workbench.js`。实际交付进度见文末验证记录：

| 能力 | 已有 | 缺口 |
| --- | --- | --- |
| 发起 / 续接 / 停止 | 真实 provider、会话 ID、后台执行、停止与退出确认 | 两个执行者都需完整真实验收；不能用一个执行者成功代替另一个 |
| 多任务 | 多条持久化任务、各自会话和成果 | 全局 active 锁仅允许一次执行一个任务；需要任务级生命周期、目录冲突控制 |
| 完整工作对话 | 已保存用户和执行者事件 | 默认突出最新回复，历史被折叠；改为连续主对话 |
| 权限 | provider 各有现存策略 | 通用事件未包含请求和回答；当前 Codex 适配方式不能完整承接桌面审批，需验证合适接口；不得以关闭审批填补缺口 |
| 成果 | 不可变文件快照、哈希、预览或下载 | 需要明确每轮成果出处及代码差异入口；进程结束不等于用户验收 |
| 子 agent / 交接 | 可点击设计样板 | 正式事件无完整父子关系和交接记录，样板不能算真实实现 |
| 外部历史 | 当前可尝试恢复 CC 已绑定的会话 | 未形成发现、浏览和导入外部历史的用户闭环 |

既有程序重启后标记 interrupted 的行为保持诚实。只有后台仍在运行或适配器确认恢复成功时，才能显示继续执行；断开连接不能显示完成。

## 实现顺序与验收

### 第一段：一个任务在 CC 内做到底

先让现有正式页面成为简洁两栏，保留完整对话、草稿和成果。为 Claude、Codex 分别完成发起、连续两轮、权限批准与拒绝、停止、查看结果的真实测试。后台运行时刷新或离开页面不会丢失任务；后台退出则正确报告中断。

这段优先于继续扩充视觉样板。只完成界面不算 CLI 替代目标达成。

### 第二段：可以同时照看几件事

不同目录的 Claude 和 Codex 任务同时执行。停止一项不影响另一项；切换任务不串消息、输入草稿、权限和文件。相同目录的冲突明确排队或使用可追溯的隔离副本，不静默并发修改。任务列表只提升真正需要用户处理的状态。

### 第三段：已有工作与明确交接

读取支持来源的历史，真实验证恢复原生会话。完成“Codex 实现 → Claude 检查 → 用户要求 Codex 按其中一条修改”：每一步有确切来源、传递内容与成果版本，原会话可追溯；同一任务里读得懂，不需要手动复制三次。

第一阶段产品目标在上述三段验收后才算完成。首次实机范围为 macOS 与用户已配置的 Claude Code / Codex；其他平台或版本未测不宣称支持。

暂不加入：通用流程编排器、常驻 subagent 树、自动选择所有模型、职业专属编辑器、跨机器进程迁移、额外内容推荐。之后根据用户实际仍需离开 CC 的原因决定下一步。

## 成功标准

连续完成一次真实的多项目工作：提出需求、执行、补充要求、处理权限、交给另一执行者检查、查看并确认成果，全程不需要打开 Claude / Codex CLI 排障或转述上下文。

如果还需要离开 CC，记录具体原因。衡量“少切走几次、少转述几次、是否可靠接得上”，不以面板数量和自动调用次数当作进步。
