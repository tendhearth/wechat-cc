# 额度恢复后接着做 —— 设计

> 2026-10-20 · 状态:**定稿,可以开工**。第二轮对标(Claude Code 2026 的 auto-continue;此前社区有包装脚本)。主人 10-20 `/loop`「继续开发…参考同类产品」。

## 为什么

一起做的事因为额度用完 / 限流停下,现在 CC 只会问「交给 X 继续?」或者说「等额度恢复再说一声」。主人得记着、得回来说那一句。大总管应该能替他等:到点了自己接着做。

**成功的样子**:微信里那条「额度用完」的通知多一句「或回「等恢复」」;主人回「等恢复」,CC 说「好,约 14:20 额度恢复,我到时候接着做(只试一次)」;到点 CC 自己续上那件事,一起做的时间线里看得见。

## 规矩(红线)

- **主人亲口选的才做**:按件,回「等恢复」/ 手机上点「恢复后接着做」才排;默认不排。
- **只试一次**:到点续一次;没接上(还没恢复、网络守护不安全、会话接不上)⇒ 写一条事件 + 微信一句,**不重试**,排程删掉。
- **到点前再核对**:任务还是那个失败状态、没被归档、期间主人没动过它(updatedAt 没变)、没有在跑的 run;任何一条不对 ⇒ 不续,删掉排程(主人已经自己处理了)。
- **有上限**:恢复时刻在 24 小时以内才排;daemon 重启后读回排程,错过超过 6 小时的不补,写一条「错过了」。
- 续接走现成的 `continueTask`(网络守护、准入、额度检查都在里面),request id 按 (任务, 排程时刻) 派生,崩了重来不会续两遍。

## 存储

`<stateDir>/quota-resume.json`:`{ [taskId]: { at, requestedAt, provider } }`(at = 恢复时刻 + 2 分钟余量)。不加迁移。

## 入口

- 微信:额度通知里加「或回「等恢复」,额度恢复后我自己接着做」;管家认「等恢复 / 恢复后接着做 / 等额度恢复」(对着待确认的接管邀请,或近期只有一件因额度失败的任务)。
- daemon 内部 API `POST /v1/workbench/quota-resume {id}`(admin)给桌面 / 手机以后用;手机 / App 的按钮由 wechat-cc-2a 接。

## 测试要钉住的

- 只在失败原因是额度 / 限流、恢复时刻 ≤ 24h 时排;重复排 = 同一个。
- 到点:条件都对 ⇒ continueTask 一次(request id 稳定);任一不对 ⇒ 不续、删排程;续失败 ⇒ 事件 + 一句,不重试。
- 重启读回:未到点的重新起计时;错过 ≤ 6h 的立刻试一次;更早的丢掉并记一条。
- 微信:「等恢复」走到排程;回话写清时刻与「只试一次」。
