# CC 为什么值得作为日常工作入口

2026-09-13。基于当前 CC 工作台实现和隔离验收证据，供后续范围取舍使用。功能仍在本地开发分支；验证通过不等于已安装版本包含这些改动。

## 用户选择的理由

只使用一个执行者、单个项目且熟悉其原生工具的人，暂时没有充分理由迁移。CC 优先服务经常交替使用 Claude / Codex、同时照看多项工作、离开电脑后还需要处理待决事项的用户。

CC 要减少的是协调成本：找到这件事、续上原会话、带着确定版本交给另一位检查、选择意见交回原任务、集中看成果和权限。执行能力来自真实原生会话。界面不能在统一之后丢失执行者的项目规则、工具能力、输入材料和公开回复。

陪伴保持在此刻和回忆中。工作入口提供持续照看与连续性，工作内容不因进入 CC 就自动成为个人记忆。

## 当前覆盖边界

| 日常需要 | 已有证据 | 明确边界 |
| --- | --- | --- |
| 在 CC 发起和继续任务 | Claude SDK / Codex app-server，完整对话、过程记录、权限和问题处理 | 不是嵌入原生 CLI 屏幕；不保证复刻每个命令与快捷操作 |
| 使用合适的模型 | 原生目录查询、任务模型与思考强度、恢复设置、实际模型回报 | 通用 API provider 不自动具备原生工具、子助手或恢复能力 |
| 使用文件和工具 | 图片/文件、项目说明及已验证的直接配置 MCP | 插件、全部 hook/skills、OAuth 与一般 MCP 管理界面不具备完整覆盖证明 |
| 同时做多个项目 | 任务/回合/请求/成果隔离，同目录排队 | 同目录安全排队不是自动独立 worktree；并发安全不能推导为任意并行写入 |
| 让 Claude 与 Codex 协作 | 已有历史导入、原生恢复、固定版本检查和选择意见交回 | 交接是明确记录的上下文传递，不是共享隐藏推理、工具内存或无损迁移会话 |
| 离开桌面后处理任务 | 微信对同一后台任务创建、查询、停止、补充、权限和问题处理；完成提醒与固定版本正文分页已有隔离 HTTP 验证 | 结果附件发送及跨电脑执行接管仍不完整；新通道功能尚未在真实微信账号验收 |
| 保留主回复之后的工作 | 后台 runtime 已通过隔离原生生命周期、回收与独立复核；见交付记录 | 不把父回复结束、后台计数为零或一段静默当作整个执行结束 |

当前不能可信地给出“CLI/App 已覆盖 80% 或 90%”。应先确定用户的任务分布，再统计无需退出 CC 的成功率。原生 App 的云端任务、专属集成或专业编辑环境不能由本地 CLI 支持推导为已覆盖。

## 更有用的专业验收

以实际任务为单位记录是否因 CC 能力缺口而必须退出，而不是按菜单项计数：

1. 在已有项目创建任务，项目要求被正确读取，用户不重复配置。
2. 在对话中补充材料、处理权限、核对执行者确实收到。
3. 主回复之后仍能看到子助手和后台命令结果；停止后确认受管理执行资源退出。
4. 两个项目同时运行，停止、权限、输入和成果互不串。
5. 中断后明确恢复原会话；不能恢复时先说明上下文缺口。
6. Codex 修改，Claude 检查，用户选定意见交回；每段结果可追溯至原任务和成果版本。
7. 报告、图片和代码差异可以在 CC 判断，必要时打开专业编辑器继续处理成果。
8. 微信与桌面处理的是同一请求；重复或过期操作不会生效两次。
9. 长任务跨日可找回，旧任务可收纳；资源占用与失败原因可解释。
10. 原生能力不支持时说明边界，保留可继续工作的材料，不用沉默降级冒充完成。

前八类稳定后，再扩展更多执行者。第三方 API 应按已验证能力接入；项目、工具、权限、恢复、媒体、后台生命周期分别声明。不同执行者不必使用完全相同的内部协议，但用户的任务入口、记录与判断方式应保持一致。
