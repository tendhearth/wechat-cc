# 连接健康:检测、降级与告警 设计

**日期**: 2026-08-03
**状态**: 已批准(对话中逐节确认)
**动因**: 2026-08-02 14:33 → 08-03 01:08,主人的 bot 静默停摆约 **10.5 小时**。`getUpdates` 连续失败 **4211 次**(TLS `unknown certificate verification error`),然后自行恢复。期间:没有任何通知、仪表盘没有信号、日志被这 4211 行刷爆触发轮转(故障起点的上下文因此永久丢失)。主人只有翻日志才知道发生过。

## 背景:现状与实证

**已经被处理的,不要重做:**

- **daemon 进程死亡** —— `launchd` 是 `KeepAlive: true` + `RunAtLoad: true`,会被自动拉起。
- **账号被接管**(ilink `errcode=-14`)—— `ilink-glue.ts` 会 flip `SessionStateStore` 让循环停止,并发一次性通知;桌面仪表盘有 `taken_over` 状态与重新扫码按钮(`dashboard.js:101`)。
- **网络探活的传感器** —— `src/daemon/guard/probe.ts` 的 `probeReachable()` 已存在,默认 `probe_url` 是 `https://www.google.com/generate_204`(`guard/store.ts:20`),已可配置,已有 CLI (`guard status|enable|disable`) 与桌面开关。

**没有被处理的(本设计的范围):**

- **传输层故障**(TLS / 网络 / 上游抖动)—— `poll-loop.ts:378-382` 的 catch 只有三行:`log('ERROR', …)` → `sleep(RETRY_DELAY_MS)` → 继续。`RETRY_DELAY_MS = 2_000` 是**固定值,无退避**(`poll-loop.ts:246`)。
- **主动外发不受连接健康门控** —— `dispatchToChat`(`wiring/tick-bodies.ts:258`)是 pushTick / gapCheckin / hunt 三条路径的唯一汇合点(调用于 :359 / :378 / :397),它内部会先跑 LLM 生成文案再发送。故障期间它照常执行:先烧 token,再往断掉的链路上发。既有的 `paused_no_reply`(`companion/calibration.ts:104`)只表示"用户没回你别再骚扰",与连接状态无关。
- **guard 的探活结论无人消费** —— `guard/scheduler.ts` 只在 IP 变化时探测并记录状态翻转日志,不驱动任何决策。
- **心跳只在成功时记录**(`poll-loop.ts` 的 `recordHeartbeat` 在成功分支),其唯一消费者是 `main.ts:75-78` 里"另一个 daemon 要不要抢锁"的判断。无兄弟进程时,陈旧心跳无人过问。

**实测(2026-08-03,主人机器):**

| 探测目标 | 结果 |
|---|---|
| `https://www.google.com/generate_204` | 204,0.87s |
| `https://www.baidu.com` | 200,1.75s(返回整页,非空响应) |

## Global Constraints

- **断线或网络不稳时,停止外发与 LLM 轮次。** 重试风暴会触发风控(见 memory `no-retry-storm-when-disconnected`)。这是本设计的首要目的,告警是次要目的。
- **不要反复探测你依赖的服务。** `generate_204` 是为高频连通性检测而生,打多少次都无所谓;`api.anthropic.com` 不是——拿未认证请求反复戳它,轻则限流,重则被视作扫描。所以**探活只用中立靶子,永不探 LLM/ilink 端点**。
- **"我坏了"这句话不能由坏掉的组件生成。** LLM 故障通知必须是写死的模板文案。
- **正常轮询是 35 秒一次**(`LONG_POLL_TIMEOUT_MS = 35_000`)。重试比这更密集没有意义 —— 这是退避封顶的锚点。

## §1 核心:每个依赖一个健康状态机

引入 `ConnectionHealth`,对**两个依赖各自独立**维护状态:`wechat`(ilink)与 `llm`(当前 chat 的 provider)。

```
healthy ──连续失败达 60s──> degraded ──成功一次──> healthy
```

只有两个状态,不设第三个。`degraded` 同时携带:首次失败时刻、连续失败次数、最后一次错误、是否已通知。

**为什么按依赖分,而不是一个全局"在线/离线":** 两者坏掉时该做的事正好相反。

| 断的是 | 入站 | LLM 轮次 | 微信外发 |
|---|---|---|---|
| **wechat** | 收不到 | 停(主动推送/问候全部暂停) | 发不出去,不要试 |
| **llm** | 收得到 | 退避到阈值后停止再试 | **发一条模板话**,只发一次 |

状态由**真实调用的成败**驱动,不由探活驱动。真实调用是最准的探针,而且免费。

## §2 双阈值:停外发要激进,通知要保守

这两件事成本差几个数量级,不能共用一个阈值。

**所有时长都从"当前这轮连续失败中的第一次失败"起算**(一次成功即清零重来),不是从上次成功起算,也不是累计时长。

- **停止外发:连续失败 60 秒。** 用时间而非次数——加了退避后"5 次失败"的实际时长会随参数漂移,而"60 秒"始终可理解。60 秒足以跨过 WiFi 切换、VPN 重连、笔记本唤醒;判断早了的代价也仅是几条主动消息延迟。
- **通知用户:按可操作性分级。**
  - **可操作 → 3 分钟。** 微信登录过期、LLM 登录/额度失效等需要主人动手的故障。不通知就永远不会好,每拖一分钟都是白白少服务。
  - **不可操作 → 15 分钟。** 网络、TLS、上游抖动。收到通知也做不了什么,且大概率自愈;15 分钟足以滤掉绝大多数自愈情况。

判定可操作性的依据是错误分类(§5),不是时长。

## §3 退避:2s 起,封顶 60s,±20% 抖动

`2 → 4 → 8 → 16 → 32 → 60 → 60 → …`,约 2 分钟到顶。

以本次事故校验:10.5 小时内 **4211 次 → 约 630 次**(减少约 85%),而网络恢复后最长 60 秒被发现,主人无感。抖动防止多账号/多实例在恢复瞬间同时冲击。

封顶取 60s 的理由是 §Global Constraints 里那个锚点:正常工作时也不过每 35 秒碰一次服务器。

## §4 门控:两个落点

- **主动外发** —— 在 `dispatchToChat`(`tick-bodies.ts:258`)入口处判断 `wechat` 健康。`degraded` 则直接 return 并记一行日志。这是唯一落点,三条 tick 路径全覆盖;且发生在 LLM 生成**之前**,所以 token 也省下了。
- **LLM 轮次** —— 入站分发路径上,`llm` 进入 `degraded` 后不再为每条新消息都发起轮次。恢复检测由**入站消息本身**驱动,并受退避约束:距上次尝试不足当前退避间隔时直接跳过(不调 LLM),达到间隔则放行一次真实尝试——成功即恢复 `healthy`,失败则退避加倍。被跳过的消息回一句模板文案,且**每次故障只回一次**(同一 `degraded` 区间内不重复,见 §5)。

被门控挡下的主动消息**直接丢弃,不排队**。它们是"此刻想跟你说句话",链路恢复后再补发就已经过时了。

## §5 通知:按状态跳变,分级,配对

**只在状态跳变时通知,不在每次失败时通知。** 一次持续 10 小时的故障因此只产生一条"坏了"。

- **恢复也必须通知 —— 但只在之前通知过的前提下。** 没说过"坏了"就冒出一句"已恢复"会让人莫名其妙。
- **没跨过通知阈值的故障,一个字都不说。** 30 秒抖动内部处理掉即可。
- **重复提醒:可操作的每 6 小时一次(自上一条通知发出起算),不可操作的不重复。** 前者你可能没看见第一条,而不处理就一直坏;后者你已经知道且无能为力,再说就是噪音。

**通道(按依赖决定,而非固定):**

| 情况 | 通道 |
|---|---|
| `llm` 断、`wechat` 通 | **微信**(模板文案,写死)+ 桌面 |
| `wechat` 断 | 桌面系统通知(`notify_user`,`lib.rs:369`)+ 仪表盘 |
| 桌面未开启 | 落库,**下次打开桌面时在仪表盘明确显示**"过去 X 小时你的 bot 是断的" |

**给用户看的是分类和结论,不是错误码。** 目标文案形如:

> 你的 bot 从昨天下午 2 点半到今早 9 点断了约 10 小时,原因是网络连接问题,现在已经恢复,你不需要做什么。

错误分类(决定可操作性与文案)由确定性规则完成:`errcode=-14` → 登录被接管(可操作);TLS/DNS/超时 → 网络问题(不可操作);LLM 401/403 → 登录失效(可操作);其余 → 未知(不可操作)。**LLM 不参与检测与投递**,它只可用于事后把故障记录翻译成人话——那是离线的、可选的,不在本设计的关键路径上。

## §6 可选探活:只诊断,永不门控

复用既有的 `guard/probe.ts`,**默认关闭**。打开后可在预设中二选一:`google.com/generate_204`(默认)或 `baidu.com`(大陆)。默认值按系统区域自动选择(`zh-CN` → baidu),多数人无需选择。

它回答的唯一问题是:**"是整个网络断了,还是只有这一个服务出问题?"** —— 用来让 §5 的文案更精确("你的网络断了" vs "微信那边连不上")。

**它绝不参与任何门控决策。** 这条是硬约束:大陆用户 `google.com` 本就不通,而用 Kimi / DeepSeek / Qwen 的用户**不需要任何代理**、LLM 完全正常——若拿探活结果做门控,这些人的 bot 会被静默锁死。关掉探活只损失一句更准的解释,不损失任何保护;打开也不可能锁死 bot。

## §7 持久化:状态文件,不做 db 迁移

故障记录用 `state-store` 的写透模式(`debounceMs: 0`,tmp+rename),存最近 N=20 条故障记录的 JSON 文件,不新增 db 表。

理由:这正是仓库既有约定说的"关键低频状态写透"(architecture-conventions §5,同 `context_tokens.json` / `user_account_ids.json`)。故障是低频事件,一个滚动列表足够;避免一次 schema 迁移,也避免 v26-v28 那类迁移风险。

每条记录:依据、开始/结束时刻、分类、是否通知过、最后错误摘要。

## §8 错误处理

- 探活失败**不算故障** —— 它是诊断增强,自身失败只是让文案退回到笼统版本。
- 通知投递失败(桌面未运行、微信也断)**不重试、不阻塞** —— 记进故障记录,下次打开桌面时补充呈现。
- 健康状态机自身的异常必须被吞掉:它是保护机制,绝不能成为新的故障源。
- 日志折叠:`degraded` 期间不再每次失败打一行 ERROR(那正是刷爆 10MB 触发轮转的原因),改为进入/退出各一行 + 每 N 次一行汇总。

## §9 测试

- **单测**:状态机(60s 判定、连续失败计数、恢复清零)、退避序列与封顶、抖动范围、分级阈值(3min/15min)、重复间隔(6h/不重复)、恢复通知的配对规则(未通知过则不发)、错误分类到可操作性的映射。
- **门控**:`dispatchToChat` 在 `degraded` 下不调用 LLM 也不发送(断言 provider 未被调用——这是"省 token"的实证)。
- **不需要真网络**:探活与调用全部注入,测试不打真实端点。
- 全量 `bun run test` + `bunx tsc --noEmit` 零错。

## 非目标

- **不做外部心跳/dead man's switch 的产品化。** 需要项目方运营一台收集所有用户心跳的服务器,与数据主权定位冲突,且成本不值。将来若做,只做一个**默认关闭、不进主界面**的高级配置项(填任意 URL:自有 VPS、Healthchecks.io、ntfy.sh 均可)——但小白理解成本高,不进新手引导。本次不做。
- **不做告警升级策略引擎、值班表、短信/Telegram 集成。** 那是团队产品的机器,这是单人 agent。
- **不做"Mac 关机/睡眠"的告警。** 本地任何机制都覆盖不了,而且主人自己知道电脑关了。
- **不改 `expired`/被接管那条既有路径**(已工作正常)。
- **不把 LLM 放进检测或投递链路。** 告警系统必须比被监控对象更可靠。
