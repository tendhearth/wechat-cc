# daemon 空闲时自动重启以加载新代码 设计

**日期**: 2026-08-03
**状态**: 已批准(对话中逐节确认)
**一句话**: daemon 发现自己跑的代码比磁盘上的旧,且当前空闲,就优雅退出让 launchd 用新代码拉起 —— 全程零界面。

## 动因

daemon 从 git checkout 运行(`bun /path/to/cli.ts run`,launchd 常驻),**bun 在进程启动时加载源码**。所以 `wechat-cc update`(`git pull --ff-only`)之后、以及任何人改了代码之后,**运行中的进程仍是旧的,直到有人重启它**。

这不是边缘情况,是**每次更新后的默认状态**:

- 2026-08-03 实测:主人机器上的 daemon 进程启动于 **7 月 27 日 22:10**。连接健康的全部修复(退避、停外发、故障记录)已经合进 dev 并躺在磁盘上,但当天 07:11 和 07:39 的两次断线,跑的仍是固定 2 秒硬打的旧代码。手动重启后才生效。
- 桌面安装包**不会**重启 daemon,所以装了新版桌面之后偏斜必然存在。

已经出现过的症状:桌面向 daemon 要 `--operator` 凭据,旧 daemon 的 `internal-api-info.json` 里没有 `operatorTokenFilePath` → 403 → 页面显示 "forbidden"。当时的处理是**手写一句错误文案**(`operator token unavailable — daemon too old`),那是为单个功能打的补丁,不是系统性的解决。

## 为什么不做版本号协商

调研了形态最接近的成熟产品:

| 产品 | 做法 |
|---|---|
| Syncthing | Web UI 由 daemon 自己提供 → 天然同版本 |
| Home Assistant | 前端与 Core 一起打包 → 不可能偏斜 |
| Docker Desktop | app 拥有 daemon 生命周期,更新 app 即重启引擎 |
| Docker CLI/daemon | 真做协商,但**用户永远看不见版本号** |
| Tailscale | `CapabilityVersion` 整数,查能力而非比数字 |

两条结论:**用户不关心版本号**(Docker/Tailscale 都把它当校验和一样藏起来);而**和本项目形态最接近的两个,选择消除偏斜而不是管理它**。

更关键的是:手动维护的协议版本号只在**契约变更**时才 bump,而本项目的真实故障是**同一份代码,一个跑旧的一个跑新的** —— 版本号根本抓不到。所以本设计不引入任何版本号或协议协商。

## §1 检测:比对 git HEAD

daemon 启动时记录它加载的 commit(`git rev-parse HEAD`,在 checkout 根执行),之后周期性对比当前 HEAD。不一致 ⇒ 磁盘上的代码已经比进程内的新。

- **每 60 秒**检查一次,挂在既有的周期 tick 上(实现时选一个已有的 tick 挂载,不新增定时器;若无合适宿主则复用 `Lifecycle` 注册一个,并在报告里说明选择)。
- `git rev-parse HEAD` 带**超时**(3 秒),超时视同读取失败。
- 任何异常(不是 git 仓库、git 不可用、命令失败、超时)⇒ **什么都不做,静默跳过**。这套机制绝不能自己变成故障源。

## §2 空闲判定:两个条件同时满足

1. **没有进行中的会话** —— 把 `SessionManager` 的 in-flight 计数暴露出来(目前是私有字段)。
2. **最近 2 分钟没有任何入站消息**(**全局**,不分 chat)—— `mw-activity` 已在每条入站上运行,由它更新一个进程内的时间戳即可,不查库。进程刚启动、从未收到入站时,该条件视为**满足**(没有对话在进行)。

2 分钟的理由:用户在对话中途思考、打字的间隔通常远短于此;而重启会打断在途轮次并让桌面断开重连,宁可多等。

## §3 动作:复用既有的重启路径

`src/daemon/main.ts:213` 的 `requestRestart` 已经在生产中使用,注释写明了机制:优雅关闭 → `exit(0)` → launchd `KeepAlive` 重新拉起。**本设计不新增任何重启机制**,只是多一个触发源。

已验证前提:该机器的 launchd plist 是 **`KeepAlive => true`(布尔形式)**,意味着**干净退出(exit 0)同样会被拉起**。若换成 `{ SuccessfulExit: false }` 的字典形式,本设计失效 —— 实现时应对此有断言或注释提醒。

## §4 零界面

不弹窗、不横幅、不显示版本号、不提供按钮。用户不需要知道这件事发生过。

唯一的痕迹是 `channel.log` 里的一行(检测到陈旧 + 决定重启),便于事后审计。

## §5 安全阀

- **不会循环**:重启后 loaded HEAD == current HEAD,条件自然不再成立。
- **最小重启间隔 10 分钟**兜底:即使 HEAD 被外部持续改动,也不会比这更频繁地自我重启。
- **启动宽限期 5 分钟**:进程启动后 5 分钟内不自我重启。重启只是为了让更新生效,晚几分钟毫无代价;而这条能挡住任何"起来就重启"的病态循环。
- **任何异常静默跳过**(见 §1)。

## §6 明确接受的取舍:重启瞬间的 POST 失败

daemon 重启会更换 internal-api 端口,桌面需要重连。而 `apps/desktop/src/api.js` 的传输层重试在 2026-08-03 被**刻意收窄为只重放 GET**(重放 POST 会重复投递笔友信件、重复烧 LLM —— 见该文件注释)。

因此:若桌面恰在自动重启的瞬间发出一个 POST,**该请求会失败且不自动重试**,用户会看到一次操作失败。

**接受这个风险**,理由:窗口极窄(仅在更新后发生一次,且需恰好撞上),轮询用的 GET 仍会自动恢复连接;而消除它需要把"空闲"再加一条"internal-api 无在途请求",为一个每次更新最多一次的窄 race 增加常驻计数,不划算。

若将来实测证明它真的困扰用户,再加那条判定。

## §7 错误处理

- 检测失败(git 不可用等)⇒ 跳过,不记 ERROR(避免刷日志)。
- 优雅关闭失败 ⇒ 沿用 `requestRestart` 既有行为(`finally(() => process.exit(0))`),不新增分支。
- 空闲信号不可得(如 SessionManager 未注入)⇒ 视为**不空闲**,即不重启。失败方向必须是"不动作"。

## §8 测试

- **单测**:陈旧判定(HEAD 相同/不同/读取失败)、空闲判定(有会话 / 有近期入站 / 两者皆无)、宽限期与最小间隔、异常全部被吞。
- **注入式**:git 读取、时钟、in-flight 计数、重启动作全部注入,测试不跑真 git、不真重启。
- 全量 `bun run test` + `bunx tsc --noEmit` 零错。

## 非目标

- **不引入版本号 / 协议协商 / 能力表**(理由见上)。
- **桌面不参与**:不检测、不显示、不提供按钮。CLI 同理 —— 它与 daemon 在同一 checkout,不可能偏斜。
- **不改 `update` 命令**:它继续只做 `git pull`,重启由本机制自然发生。
- **不做"重启前通知用户"**:这与"零界面"直接冲突。
- **不处理"旧桌面 + 新 daemon"**:路由是增量添加的,旧桌面只调旧路由,该方向基本安全。
