# 一段对话 + 话题泡泡(终态方向,2026-11-05)

> 状态:**方向稿**。主人 11-05 提出、当天定了三点(见「主人已定」)。后面的分步各自再出设计稿;看得见的那几步(T4、T5)动手前再点头。

## 起因(主人原话的意思)

- 现在 GPT / Claude 把「聊天」和「干活」(chat / cowork)分成两个入口,产品上不对,用户也困惑。CC 自己的「一起做」和「此刻」两页也是这个割裂:像,又不像一套产品语言。
- 想要的是 dots / Muse / Grok Bot 那样的统一入口、大管家。但它们有个问题:和 dot 聊多了,上下文不够用。
- 跟朋友聊天永远是一个上下文窗口;让朋友做过的事,以后提到时才去想起相关的记忆。项目只是项目,但很多活跨项目、跨资源、跨 agent(Codex 出图、Claude 执行、DeepSeek 测试)。agent 之间应该共享上下文,主人和 CC 聊起某个话题,也该知道以前聊过的。
- 主人自己的 `~/Documents/claude_杂事` 很杂,但靠标签化整理(一条事实一个文件 + 一行一条的索引),聊到「服务器」就知道以前存过的服务器记录 —— 聊到某个话题才打开更详细的内容,和人与人聊天一样。

## 对标(11-05 查的,来源多为二手)

| | 入口 | 记忆 | 干活 |
|---|---|---|---|
| OpenAI dots | 一个 dot 多处可达(桌面 / 网页 / 手机 / Slack / Teams),仍分多段「对话」 | ChatGPT 记忆 + 自己的私有记忆;单条看不到、删不了,只能删整个 dot | 自己一台云电脑;Activity View 能看能接管;敏感步骤交回给人 |
| Meta Muse | App / Mac / WhatsApp | `Memory.md` + `Soul.md`(人格,几乎照搬 OpenClaw)+ `Identity.md`;会话开始时读 | 内部子 agent;外发要 Sentinel 批准 |
| Grok Bot | 和 Grok 聊天分开的另一个产品 | 资料少 | 自己的云电脑,bot 之间能协作 |

共同点:**一个助手 + 若干段对话 + 一整块记忆**。记忆不按话题拆,所以聊久了要么装不下、要么想不起来(主人说的「dot 上下文不够用」)。HN 上也有人说 Codex / ChatGPT Work / Dots 的边界越来越糊 —— 就是主人说的割裂。

## 终态

1. **只有一段对话:主人和 CC 的。** 没有「聊天」「干活」两个入口。上下文窗口不是一路堆的聊天记录,而是**每一轮现拼**:最近几句 + 关于主人的那份总记忆(`memory.md`)+ 这一轮提到的话题调出来的那几条。窗口永远不会被聊满。
2. **CC 管三样,各管各的:**
   - **话题**:记忆的单位(主人说的标签)。天然跨项目、跨资源、跨 agent:「服务器」「bx」「writter」。
   - **agent**:手下。谁擅长什么、谁有额度、谁在忙。
   - **一件事(matter)**:派出去的活,带着当时的过程(MatterLog)。
   - **项目**只是一种资源 —— 话题挂着的一个文件夹,是一个切法,不是容器。
3. **不要「群」。** 群是给人的(人需要同时在场)。agent 要的是共享上下文,CC 当中枢就够:派活时从话题里拣一份**简报**给它;做完把过程和结果**写回话题**。agent 之间不用互相看聊天,共享的是 CC 记的那本账。下次主人聊到这个话题,不管上次是谁干的,CC 都知道。
4. **话题泡泡**:聊到某个话题,旁边冒一个泡泡 —— 上次聊到哪、相关的几条记忆、正在跑的活。平时收着,点开才看。

## 主人已定(11-05)

- **话题由 CC 定**:CC 自动抽、自动合;主人可以改名、合并、删(同 `claude_杂事` 的用法)。
- **CC 睡一觉,泡泡就关**:每晚整理记忆(`src/features/memory/nightly.ts`,04:00)就是收尾 —— 把当天聊到的每个话题整理成几条,泡泡收起;再聊起,带着整理好的内容重新冒出来。
  - 例外(整合者提议,随 T4 稿再确认):话题下还有在跑 / 等批准 / 等回答的活,泡泡不关,做完后下一觉再收。
- **快速切换**:输入框上方一排最近的话题(5–8 个,按最后聊到的时间),点一下打开那个泡泡。是标签,不是另一个聊天窗口。

## 现在已有的零件(11-05 真库)

- **一段对话**:主人那条 chat matter 唯一一条;微信 / 桌面 / 手机三处的话落进同一个 `messages` 流(797 条)。
- **一件事**:258 件 task、124 个 terminal、1 件 act,都在 MatterLog。
- **话题**:`threads` 表(v14,`src/daemon/threads/extractor.ts`,由 `src/features/companion/tick-introspect.ts` 触发)已经有标题 / 摘要 / 标签 / 状态(active / dormant / done)/ episodes。**但真库只抽出 8 个**,而且:
  - 抽取时跳过 `source = 'workbench'` 的消息 ⇒ agent 干的活不进话题;
  - 只给陪伴的自省用,**对话每一轮不按话题调记忆**;
  - 和 matter 没有关联。
- **总记忆**:每晚整理的 `memory.md`(五栏、3000 字上限)—— 适合「关于你」,装不下一个个话题。
- **知识层**:wxfacts / wxgraph(另一套,本稿不动)。

## 分步(每步一份设计稿;前三步只动 daemon,主人看不到界面变化)

- **T1 话题升格**:话题的记忆按「一条一件事 + 一行一条的索引」存(学 `claude_杂事`),标签由 CC 定;抽取覆盖主人的对话和 agent 的活(去掉对 `workbench` 的整批跳过,改成只抽结果与结论)。现有 8 个话题迁过来。
- **T2 每一轮按话题调记忆**:CC 回话前先看这一轮碰到哪些话题(先匹配索引,便宜模型兜底),把那几条放进上下文;没碰到就只有总记忆。门:同样的问题,换个说法也能调出同一条(评测样本进 `eval`)。
- **T3 一件事挂话题**:派活时从话题生成简报交给执行者;做完把结论写回话题。跨 agent 共享上下文就是这一步。
- **T4 泡泡与睡一觉收起**(看得见,要点头):话题的开 / 关状态、每晚收尾、活没完不关、快速切换那一排。daemon 出数据,桌面 / App / 网页各自画。
- **T5 一段对话的界面**(看得见,要点头,桌面与 App 都要发版):「一起做」与「此刻」合成「一段对话 + 旁边的泡泡 + 一排话题」。U4b 那份一套语言的稿子按这个重排。

## 不做 / 推后

- 群聊、agent 互相看对方的聊天:不做(见终态第 3 条)。
- 记忆单条看不到 / 删不了(dots 的做法):不学。CC 的话题记忆主人看得见、改得了。
- 把知识层并进话题:推后,先看 T1–T3 的效果。

## 风险

- **调错记忆比没调更糟**:T2 先只在主人对话里开,带评测;调进来的几条在泡泡里看得见,主人能说「这条不对」(接现有的记忆纠错)。
- **话题抽得太碎或太粗**:真库现在 8 个是太少;T1 的提示词按 `memory.md` 吃过的亏写(一条一件事、承诺单独放),先拿真库副本试跑给主人过目。
- **成本**:每轮多一次匹配。先索引精确匹配,模型只兜底,并且走便宜模型。
