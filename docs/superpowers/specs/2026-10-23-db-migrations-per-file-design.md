# 迁移一版一个文件(第三批 3e)设计稿

> 2026-10-23 · wechat-cc arch-review 起草,待 wechat-cc-9d 审。上位:`docs/architecture-review-2026-10-21.md` §3e「`db.ts` 一版一个文件,老夹具从真迁移起步,删掉九个迁就测试的守护」。

## 1. 现在是什么样

- `src/lib/db.ts` 2005 行,`migrations` 是一个 84 项的数组字面量,每项一个箭头函数,注释 `// vN — …`。
- `runMigrations` 先跑 `repairBranchRenumberedSchema`(#79 的修复,只认 user_version 19–21 的那个签名),再从 `user_version` 往后跑,每跑一项 `user_version = index + 1`。
- 守卫:`migration-order.test.ts` 锁每个已发布版本**新建库**跑出的 schema 指纹;`db.test.ts` 里有若干条「升级路径」用例(`migrations.slice(0, N)` 跑到旧位置,再按旧形状改表,再跑完)。
- 迁移体里有一批「为测试让路」的守卫(表在不在、列在不在),注释写着「db.test.ts 有从 user_version=9 / 26 起跑的夹具」—— 三个夹具(`db.test.ts:129 / 159 / 206`)手写了一个假的旧库,声称自己在 v9 / v26,但表和真 v9 / v26 不一样。

## 2. 问题

1. 一个 2000 行的文件,每加一版都在末尾改它;两路同时各加一版必冲突(冲突本身是好事 —— 见 §4 —— 但冲突在 2000 行文件的末尾,很难看出是「位置冲突」)。
2. 那批「为测试让路」的守卫让迁移体越来越难读,而且它们保护的是**不存在于任何真机上的 schema**。新写迁移的人照着抄,于是一直在长。
3. 假夹具测的不是用户真正走的那条路(和 v49 那次同一个家族:测试从不走用户的路)。

## 3. 做法

**文件**:`src/lib/db/migrations/v001.ts` … `v084.ts`,每个文件导出一个 `migration: (db) => void` 和一行 `summary`(就是现在的 `// vN — …` 注释)。迁移体**逐字搬**,一个字符都不改(含那批守卫,见 §5)。

**顺序只在一处、手写**:`src/lib/db/migrations/index.ts`

```ts
import * as v001 from './v001'
…
import * as v084 from './v084'
export const migrations = [v001, v002, …, v084].map(m => m.migration)
```

**不扫目录、不按文件名排序**:顺序是契约,必须是一行一行写出来、在 diff 里看得见的东西。目录扫描会让「多了一个文件」悄悄变成「多了一个迁移」。

`db.ts` 留下 `openDb` / `runMigrations` / repair / `withLockRetry` 和几张 `initialize*Schema`,从 `./db/migrations` 引 `migrations`。`export { migrations }` 照旧从 `db.ts` 转出,外部 import 不变。

## 4. 计数怎么保证不变(9d 要求的一节)

`PRAGMA user_version` 记的是**跑了几个**,不是哪几个(#79 的根因)。所以拆文件这一步必须证明「第 i 项还是原来的第 i 项」,而且以后也不会被悄悄挪动。三道:

1. **搬家这一步本身**:PR 里带一个一次性校验(跑完删掉,不进仓库):拆前拆后各对 84 个函数取 `fn.toString()`,逐项相等。这证明的是「逐字搬、顺序没动」;再加上 `migration-order.test.ts` 的指纹全部原样过(新建库跑出来的 schema 不变)。
2. **文件名 = 位置**,守卫测试钉住:`index.ts` 里第 i 个 import 必须是 `./v{i 补零到三位}`,`migrations.length` 等于目录里 `v*.ts` 的个数,编号连续、不跳号、不重号。于是:
   - 有人在中间插一个文件 ⇒ 后面的文件名全对不上 ⇒ 红;
   - 两路各自加了 `v085.ts` ⇒ 合并时**同名文件冲突**(比今天「数组末尾各加一项、git 自动合成两项」更好:今天两项会被静默合并成 v85、v86,其中一路的库就和 #79 一样错位)。
3. **进了 dev 的就不许改**(9d 审稿改的:「发版时锁哈希」一靠人记、二冻得太晚 —— 主人真机跑的就是 dev,迁移一合进 dev、
   部署一次,就已经在他的库里跑过了)。CI 里一步检查:拿这个 PR 改到的 `src/lib/db/migrations/v*.ts` 跟 `origin/dev` 上的
   同名文件比,**dev 上已经有的必须一字不差,只有新加的文件能改**。不用维护哈希表,冻结时刻跟部署节奏对得上。
   紧急要改老迁移走显式豁免:PR 标题带 `[migration-edit]`、描述写理由(检查读 PR 标题放行)。
   这一条和指纹守卫互补:指纹只看新建库的结果,v49 / v59 那类「只修存量库」的改动指纹看不出来,这里看得出来。
   实现:`scripts/migration-frozen.ts`,CI 的 build 作业在 `actions/checkout` 用 `fetch-depth: 0` 之后跑;本地没有
   `origin/dev` 时跳过并说一句(不在本地挡人,挡在 CI)。

## 5. 「删掉九个迁就测试的守护」—— 这里改主意了

复查时写的是删掉。动手前核了一遍,**不删**:

- 它们在**已发布的迁移体里**。改它们就是「改已发布的迁移」,§4 第 3 条恰恰要禁止这件事。
- 对真机它们是空操作(表本来就在),但 #79 的 repair 会把 `user_version` 倒回 18 让 v19 以后**重跑**;重跑时这些「表在不在」的守卫是不是在帮忙,没法逐条证明不是。不改,就不用证明。

改成两条往后的规矩:

- **新迁移不再写「为测试让路」的守卫**:守卫测试里加一条规则,v085 起的文件里出现「db.test.ts 有从 user_version=… 起跑的夹具」这类注释 ⇒ 红。
- **假夹具改成从真迁移起步**:`db.test.ts:129 / 159 / 206` 三个夹具改用 `migrations.slice(0, 9)` / `slice(0, 26)` 跑出真的 v9 / v26,再造它们要测的那个状态。改完以后旧守卫成了真正的死代码,但留着(理由同上),注释改成「历史上为假夹具加的,已无测试依赖,留着是因为不改已发布迁移」。

## 6. 切法

1. 搬家:84 个文件 + index + 一次性逐项 `toString` 校验(PR 描述贴结果)+ 文件名 = 位置的守卫。行为不变。
2. CI 检查「进了 dev 的迁移文件一字不差」+ `[migration-edit]` 豁免(§4 第 3 条)。
3. 三个假夹具改从真迁移起步;新迁移不许写「为测试让路」守卫的规则。
4. `docs/maintainer/migrations.md` 改写「怎么加一个迁移」:新建 `vNNN.ts`、在 index 末尾加一行、跑测试;合进 dev 之后它就冻住了。

## 7. 不做

- 不改任何迁移体、不改 `runMigrations` / repair 的逻辑。
- 不换迁移机制(不上「记哪几个跑过」的表):`user_version` 是计数这件事本身不坏,坏的是位置能被悄悄挪动;§4 把「挪动」变成必然的冲突或必然的红,够了。
