# CC 自己跑开发:主人只说要做什么(设计稿)

2026-10-23 · 状态:设计稿,**重构(第三批)做完再开工**(主人 10-23 拍板:「先写设计稿,重构做完再开工」)

## 1. 为什么

主人 10-22:「希望以后我可以直接用 cc 而不是通过 claude / codex 下达任务。」

现在的开发是这样跑的:主人在 Claude Code / Codex 终端里开两路会话,一路写代码,一路当整合者(审、合、部署、汇报),两路之间用会话消息协作。主人只在要拍板的时候出现。这套做法这两天(10-21 到 10-23)合了 #497–#587 将近一百个 PR,抓到过一串真问题。但入口是终端,而且主人得自己开会话、自己当调度员。

目标:主人在微信 / App / 桌面对 CC 说一句「把 X 做了」或者「继续做重构」,CC 自己拆活、派执行者、互相评审、过闸门、合进 `dev`、部署、真机核对,只在真要主人拍的事上问他,其余用人话汇报。

这正是 CC 的定位:agent 之上的编排 + 多端(见 `positioning-replace-paseo`、`overseer-direction`),不是让主人去当编排者。

## 3. 缺什么(两路会话做了、自改做不了的)

按这两天真发生过的事列,每一条后面是它挡下来的东西:

1. **拆活。** 「继续重构」要变成一串有先后的小 PR,叠着走(父 PR 合了,子 PR rebase、改 base、关掉再打开才跑 CI)。自改一次只认一条需求。
2. **并行开发,一个整合者串行合。** 两条线同时写,合并只有一个人按顺序做;撞了 BASELINE 谁后合谁 rebase。自改一次只跑一条,也没有队列。
3. **换人评审。** 评审要有独立视角,而且评审能真改结论:#545 抓到「坏了说成关了」;#546 抓到总览拿开机时状态跟现在配置对不上;#542 抓到 start 段上游坏了下游照跑;#569 抓到 self-change 会因配置坏半路崩;#576 引出符号链接被替换;#579 引出「被撤掉的那句会在串门时说给外人听」。自改的评审是同一家(Claude)的另一个会话。
4. **判读 CI。** 什么是 flake、什么是真红,要读日志、读抛错的那行代码再下结论。几次真红都是这样分出来的:#569 的两条、#546 的 e2e 快照、#537 自己写的平台相关测试。
5. **看机器忙不忙。** 主人在打游戏或跑模拟器时(load 100–240),本机全量既拖慢他、结果也不可信 ⇒ 以 CI 为准;部署要等他不用机器。自改不看这个。
6. **部署后真机核对。** 不只是自检 PASS:看关机行顺序、配置文件键数和权限位、有没有残留 tmp、锁等待那一行。每一批核的东西不一样。
7. **知道什么该问主人。** 改了主人每天看得见的行为(Cursor 改成逐条弹卡、桌面总览变只读)要问;纯重构不问;发版、TestFlight 永远问。两路会话里有一次差点按旧授权自己定了(Policy 第 5、6 步),被拦下来了。
8. **用人话汇报。** 汇报说的是「对主人意味着什么」,不说 PR 号和文件名。
9. **做法清单。** 上面这些都靠两路会话的记忆和笔记在撑,CC 自己读不到。

## 4. 设计

### 4.1 一个「开发目标」是一件事

主人说「把 X 做了」⇒ 建一件 `matter`,类型 `dev_goal`,挂在这个仓库上。三端都看得见它的进度:计划、每个 PR 的状态、在等主人拍什么、花了多少钱。主人在任何一端都能说「停」「先别部署」「这条不要了」。

### 4.2 四个角色,只有两个是模型

| 角色 | 是什么 | 做什么 |
|---|---|---|
| **规划者** | 模型(一个执行者会话,只读) | 读需求、读代码、读 `docs/`,产出一份计划:要改什么、拆成几个 PR、先后和依赖、哪些步骤改变主人看得见的行为。大改动先写设计稿(跟现在一样,设计稿本身也是一个 PR) |
| **开发者** | 模型(工作台执行者,独立工作区) | 一个 PR 一个工作区,实现 + 本地验证(看负载决定跑全量还是跑相关目录)+ 开 PR |
| **评审者** | 模型,**跟开发者不是同一家**(缺省开发者 Claude ⇒ 评审 Codex,反之亦然) | 只读;读 diff、读周围的代码、自己跑能跑的检查;给 verdict + findings。findings 回给开发者修;两轮修不掉、或者两边意见相左 ⇒ 问主人 |
| **整合者** | **代码,不是模型**(daemon 里的合并队列) | 按计划的先后等 CI、调 `ci triage`、flake 重跑、真红交回开发者、叠着的子 PR 自动 rebase 改 base 重开、按顺序 squash 合 `dev`、一批合完排部署 |

整合者做成代码,是因为这两天它做的事几乎都是确定的:顺序、等绿、重跑、rebase、`--match-head-commit`。模型只在判断处出现:「这条红是不是这个 PR 造成的」交给评审者,读日志和抛错那行代码再说成因(`read-code-before-naming-flake-cause`)。

### 4.3 做法清单:CC 读得到的规矩

新建 `docs/maintainer/practices.md`,一条一条写,每条带出处(哪个 PR、哪次事故)。规划者、开发者、评审者的提示词都引用它。起始清单就是这两天的:

- 跑全量前先看负载,主人在用机器就以 CI 为准;两个执行者不同时跑全量。
- 改到命令路由必跑 `test:e2e`(#546 漏过一次)。
- 推之前跑整个目录,别只跑「相关的」(#569 漏过 `src/lib` 的仓库守卫和 `src/cli/self-change`)。
- 偶发红先读抛错的代码再说成因;「与本 PR 无关」要有证据。
- 改变主人看得见的行为 ⇒ 停在设计稿里等主人;授权不外推到「天天看得见」的变化。
- CC 不骗人:坏了不说成关了,没核实的写 none,已知限制写进稿子和测试。
- 守卫读源码先把 CRLF 统一成 `\n`;去注释按行判,别用跨行正则(#541、#568 两次)。
- 叠着的 PR:父 PR squash 后,子 PR `--onto origin/dev`、改 base、关掉再打开。
- 别在还有 pending 检查时合。
- 已经进 `dev` 的迁移一字不改(#583 由 CI 守)。
- 存密钥的文件每次写都给 0o600;写主人家目录配置要跟随符号链接。

清单本身由守卫检查格式(每条有出处),新增一条走 PR。

### 4.4 闸门:单个 PR 沿用自改的,加一层「一批」

**单个 PR:** 沿用自改的五道(禁改清单 → 本地测试 → 评审 → CI → 合并),只改两处:评审换成另一家;CI 交给整合者的队列,不再每条自己等。

**一批:** 一组 PR 合完以后、部署之前,整合者要做四件事:

1. **看负载**:load 高或主人刚在动机器 ⇒ 不在本机跑全量,也不构建,等;修 bug 的批次例外,但要在汇报里写明。
2. **全量**:机器空着才跑;不空就以各 PR 的 CI 全量为准,汇报里照实写「本机没跑」。
3. **部署 + 自检**:`self deploy`,然后 `selftest workbench` + `selftest chat`。
4. **真机核对**:计划里每个 PR 可以写「部署后要看什么」(比如「日志里有 `stopped knowledge/store close`」「agent-config 键数没变」),整合者照着查,查不到就停下来汇报,不继续下一批。

### 4.5 什么时候问主人(准绳)

一律问:
- 改变主人日常看得见的行为(界面、微信里的说法、执行者会不会弹卡);
- 发版、TestFlight、任何对外的动作;
- 碰禁改清单;
- 花费超过这个目标的预算;
- 评审和开发两轮谈不拢。

不问、做完汇报:纯重构、修 bug(行为回到本来该有的样子)、测试、文档、守卫。

问的方式:一张 blocking 卡,写清选项和我的推荐,跟现在两路会话问主人的口径一样。主人不在线时,这一件停在那里,其他件照走。

### 4.6 汇报

- 每合一批:一条 report(人话:「这批之后,你的配置文件不会再因为同时写坏掉」),附 PR 链接,但正文不讲 PR 号。
- 每天一次总结,跟日报合并。
- 卡住了(真红修不掉、等拍板超过一天)单独说一句。

都走 SpeechPolicy:免打扰时推后,断线时排队,不重试风暴。

### 4.7 预算、停机、并发

- 每个开发目标有预算(主人给,或者缺省值);到了 80% 说一句,到了 100% 停下来问。
- 沿用自改的 `fail_streak` 停机:连续失败 N 次 ⇒ 停机,`--unhalt` 才能继续。
- 同一个仓库同时最多两个开发者工作区、一个整合者;全量测试同时最多一个。

## 5. 不做

- **不自己发版**,不碰 `master`,不传 TestFlight:这些永远要主人点头。
- **不改禁改清单里的东西**,包括这条流水线本身的闸门代码(防止它把自己的护栏改松)。
- **不用免审执行者(agy)当开发者**:它收不住任何工具面(#567 的 confines 全是 none)。
- 第一版只管这一个仓库(wechat-cc 自己)。主人的其他项目以后再说。

## 6. 怎么分步(重构做完以后)

每步一个或几个 PR,单独能合、单独能停。

1. **做法清单成文件**:`docs/maintainer/practices.md` 加格式守卫。只有文档。
2. **评审换人**:自改的 review 步改成另一家执行者;findings 回路不变。这一步做完,现在的「自改」就已经比今天强。
3. **合并队列(整合者)**:daemon 里一个确定性的队列。输入是一串有先后的 PR,它负责等 CI、triage、重跑、叠 PR 的 rebase / 改 base / 重开、按序合。先只给自改用。
4. **一批的部署门**:负载判断、全量、部署、自检、真机核对清单。
5. **规划者**:目标变成计划和 PR 列表;碰到「主人看得见的行为」自动停在设计稿等拍板。
6. **并行开发**:两个工作区,按依赖图排。
7. **入口**:微信 / App / 桌面「开发 <目标>」,挂成 `dev_goal` 这件事,三端看进度、能叫停。

1–4 做完,主人就能在微信里说「自改 X」,得到的是今天两路会话的质量;5–7 才是「继续做重构」这种整件的目标。

## 7. 风险

- **花钱失控**:四个角色都是会话。⇒ 预算硬顶,规划者和评审者用便宜一档的模型,只有开发者用最好的。
- **没有人在看就合了坏代码**:评审换人加 CI 加真机核对是三层,主人看得见的行为仍然要拍板。合进 `dev` 不等于发版。
- **CI 不稳导致白烧**:Windows 工作台超时这类已知 flake 由 triage 认;同一个 PR 重跑两次还红就当真红,交回开发者。修 Windows 超时本身(工作台测试留着打开的文件)是重构里的一项欠账,要先做掉。
- **改自己的流水线**:流水线代码在禁改清单里,要改走人(主人或终端会话)。

## 8. 要主人拍的

1. **缺省的开发者 / 评审者搭配**:推荐 Claude 写、Codex 审;主人也可以反过来,或者指定。
2. **每个目标的缺省预算**。
3. **合进 `dev` 和部署要不要每次问**:今天的自改是每条都要回 y。推荐:纯重构 / 修 bug 合完直接部署、事后汇报;改变看得见的行为的仍然逐条问。
