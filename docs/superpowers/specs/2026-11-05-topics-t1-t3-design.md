# 话题 T1–T3 设计稿(2026-11-05)

> 方向稿:[`2026-11-05-one-conversation-topics-direction.md`](2026-11-05-one-conversation-topics-direction.md)。
> 这三步只动 daemon,界面不变。主人**看得见**的地方每节单独标「看得见」。

## T1 话题升格

### 存法(v104)

学 `claude_杂事`:一条一件事,一行一条的索引,聊到才打开。

- **话题** = `threads` 表的一行(id 不变,老的 8 个原地升格)。新加一列 `aliases`(JSON 数组):CC 定的「主人会怎么叫它」——
  简称、英文名、口头说法(「那台 mini」「bx」「服务器」)。T2 的索引匹配就靠 标题 + 标签 + 别名。
  - 标题改成「主人嘴里的那个词」(≤ 12 字,像 `bx`、`服务器`、`writter`),摘要当这一行索引的钩子(≤ 60 字)。老标题太长的,
    抽取时允许 CC 改短(id 不变)。
  - `tags` 照旧,由 CC 定、跨话题共用(词表优先复用)。
- **条目** = 新表 `topic_entries`,一行一件事:
  - `kind`:`fact`(事实 / 配置 / 地址)、`decision`(定了什么、为什么)、`commitment`(谁答应谁什么,可带 `due`)、
    `progress`(做到哪一步)、`conclusion`(一件活的结论)。**承诺单独一类**,不和事实混在一行(`memory.md` 吃过的亏)。
  - `line`:索引那一行(≤ 60 字,带关键词,像 `MEMORY.md` 每行的钩子);`body`:细节(≤ 300 字,可空)。
  - `status`:`live` / `done`(承诺兑现、活做完)/ `superseded`(被新的推翻)。只标,不删 —— 推翻留痕。
  - `source`:`chat`(主人的对话)/ `work`(agent 的活)/ `delegate`(T3 一次咨询);`matter_id` 指回那件事。
- **抽取位置** `thread_extract_state` 加两列:`entries_to_ts`(对话的新水位)、`work_cursor`(MatterLog 的 `matter_items.cursor` 水位)。
  老的 `extracted_to_ts` 不再读、原样留着(冻结的列不删)。

### 老数据怎么迁

- `threads` 的行原样保留(id、标题、摘要、标签、episodes 都不动);`aliases` 先填成它的 `tags` 里**只有它自己用**的那几个
  (「bx」)。几个话题共用的大类(「产品开发」)不当别名 —— 真库副本试跑时这么填过,一句话说到「产品开发」就同时碰到六个话题。
- 新水位从空开始 ⇒ 下一次抽取**把历史从头按新格式再读一遍**,老话题作为「已有话题」交给模型,往里补条目、必要时改短标题,
  不重复建。episodes 在存的时候合并重叠段,重读不会叠出重复的时间段。
- 历史一次读不完:按字数切批(每批 ≤ 24k 字,输出要装得下这一批的全部操作),一拍最多跑 8 批,剩下的下一拍接着(真库 797 条 + 约 150 段 agent 结论,一拍读完)。

### 抽什么

- **主人的对话**:`messages` 里这个 chat 的所有来源(微信 / 桌面 / 手机)。`source='workbench'` 那几条仍不进 —— 它们是 CC 发的
  「任务 xxx 已答复」通知,内容是下面 MatterLog 结论的复印件,进了会算两遍。
- **agent 的活**(只在主人的对话上抽):MatterLog 里 task / terminal / act 三种 matter,每段「主人说一句 → agent 做完」只取
  **最后那条 agent 回话**(结论),带上那句要求(≤ 200 字)和这件事的标题 / 项目 / 状态。过程(工具调用、中间的话)不进。
  - 一段算「做完了」:后面又有主人的话,或者这件事已结束(done / failed / cancelled),或者最后一条已经过去 30 分钟。没做完的段
    不读、水位停在它前面,下一拍再看。
  - 自检 / 草稿目录里跑的(已知机器标题 `selftest` / `selftest-phone` / `selftest workbench` 等,或路径在系统临时目录下)不算主人的活,跳过。

### 提示词(按 `memory.md` 的教训写)

- 一条只写一件事;一个配置一条、一个决定一条。一句话里有两件事就拆两条。
- 承诺单独放(`commitment`),有日期写 `due`;兑现了用 `update_entry` 标 `done`,不新建。
- 新说法推翻旧条目:旧的标 `superseded`、再加新的;不在旧条目上改意思。
- 话题建得比以前松:以前「≥10 轮或第二次出现」才建,真库一共只抽出 8 个。现在:有一条值得以后想起来的事,而且它属于一个以后
  还会聊到的东西(一个项目、一台机器、一个人、一件持续的事),就建;寒暄、一次性的问答不建。
- 不记密码、密钥、令牌原文(写「密码在 X 处」)。
- 日常流水(哪个提交、CI 修了哪个测试、版本号一路往上)不记,除非它就是结论;同一件事有新进展就改旧的那条 progress。
  (试跑第一版时 bx 一个话题堆了 14 条,一半是提交号。)
- 已有话题标题超过 12 字或带「」的,这一批就改成一个词;别名里不放大类词(那是 tags)。
- agent 结论只记结论(改了什么、结果是什么、卡在哪),不记过程。
- 便宜模型失败的处理:空输出 / `EvalOutputExhaustedError` ⇒ 同一批重试一次;再不行这一批不动水位,下一拍再来。
  解析失败同样不动水位(和以前一样)。

### 看得见吗

**看得见(轻微)**:桌面「对话」页的话题卡片(`apps/desktop/src/modules/dialogue-page.js`,走 `GET /v1/dialogue/threads`)
画的就是 `threads` 表 —— 迁移后第一次抽取完,卡片会从 8 张变多、老标题可能被改短。卡片的样子不变,条目不出现在卡片上
(接口不加字段以外的东西)。`wechat-cc dialogue threads` 同理。

## T2 每一轮按话题调记忆

### 什么时候调、调进哪

- **只在主人自己的对话**(`companion.default_chat_id`),两条进来的路都调:微信入站在 `mw-recall`(消费者之后、分发之前,
  只有真进对话的话才付这一下),桌面 / 手机在 `wire-converse` 的 `submitTurn` 之前(App 那一轮不走入站管道)。
- 调出来的放进这一轮的信封(`formatInbound`),在 `<recall>` 前面一个 `<topics>` 元素。系统提示词不动 —— 总记忆
  (`memory.md`)照旧在会话起来时注入;**没碰到话题就什么都不加**,信封和以前逐字节一样。
- 一轮最多 2 个话题、每个话题最多 6 条(先放和这句话最相关的,再按新近;还没兑现的承诺排前面),整块 ≤ 1200 字。
  只放 `live` 的条目;话题标 `done` 的不调。

### 怎么判这一轮碰到哪个话题(先索引,模型兜底)

纯函数 `src/domain/topic-match.ts`,零 I/O:

1. **精确**:话题的标题或某个别名原样出现在这句话里(英文按词边界、不分大小写;中文至少 2 个字)⇒ 直接算碰到。
2. **近似**:这句话切成中文二字词 + 英文词,和每个话题的「标题 + 别名 + 摘要 + 条目索引行」比重合;重合够多、
   且明显高过第二名 ⇒ 算碰到。只有一个话题沾边、撞上了两个不同的词,也算碰到。
3. **拿不准**(两个以上话题都重合了一点、分不开):只把这几个(≤ 5,各带 3 行最相关的条目索引)交给便宜模型,回编号或 0。
   模型超时(3.5 秒;真库副本上量过,生产的便宜模型回一个编号要 1–3.2 秒)/ 出错 / 空输出 / 回的不是单个数字 ⇒ 当作没碰到,这一轮照常回。**一点都不沾的话不叫模型。**

> 2026-11-07 T7 修订（替代原来的模型触发与条目选择规则）：索引零候选时，去掉标点/空白后至少 12 个字母或数字、且含至少 3 个不同非停用词的句子，交最近活跃的 5 个未 done 话题给回合内快判；短句和寒暄不增加模型延迟。与 ambiguous 路径共用提示词/严格解析，每题按原顺序列至多 12 条索引、每条截到 100 字符，接受 `2` 或 `2.3`；点名条目优先进入信封与 entryIds，条目越界只认话题。两路同受 2.5 秒预算，0/乱回/出错/超时均不召回，日志记录 via、reason（zero-candidates/ambiguous）和 elapsedMs。

换个说法也能调出同一条,主要靠 T1 抽取时 CC 给话题定的别名(「那台 mini」「91」「服务器」),不靠每轮叫模型 —— 成本挪到每天一次的抽取里。

### 成本

- 每轮:两次本地查询(话题 + 条目),纯字符串比对。只有「拿不准」的那一小部分轮次多一次便宜模型调用(≤ 5 个候选,提示词 < 2k 字)。
- 便宜模型走 `registry.getCheapEval()`(生产那一个,带网络守护)。

### 评测(门:换个说法也能调出同一条)

`eval` 加一类 `topic`:样本自带一小份话题(像 `reference` 自带候选),daemon 用生产的匹配 + 生产的便宜模型跑,
新硬规则 `{"recalls":{"topic":"…","entry":"…"}}` / `{"recalls":null}`(什么都不该调)。样例在 `eval/output/examples/topic-*.json`:
同一条条目,三种问法(原词 / 别名 / 换说法)都要调出来;闲聊一句不该调。六条样例只靠索引就全过(单测
`src/daemon/threads/recall.test.ts` 每次都跑一遍);便宜模型只在两个以上话题分不开时才上。

### 看得见吗

**看得见**:CC 回话会带上以前聊过、agent 做过的事(这是这一步要的效果);调错了也会看见(风险里写的「调错比没调更糟」)。
拿不准、去问便宜模型的那几轮会慢一点(1–3.5 秒)。界面不变;调进来的那几条现在看不到(T4 泡泡里才看得到)。

## T3 一件事挂话题

### 存法(v105)

新表 `matter_topics(matter_id, thread_id, attached_ts, written_back_cursor)`:这件事挂在哪几个话题上、结论写回到 MatterLog 的哪一条
(`matter_items.cursor`)。一件事可以挂几个话题;话题删了跟着删(外键 CASCADE)。`matter_id` 不加外键 —— delegate 一次咨询没有 matter。

### 派活时:从话题生成简报

- **工作台任务**(`features/workbench/service/execute.ts`,起执行者那一刻):主人的任务(`task.ownerChatId` 是主人的对话)才做。
  拿「任务标题 + 这一轮的要求」去话题索引里匹配 —— 和 T2 同一个匹配,**只用索引、不叫模型**(起执行者不该多等一个模型)。
  碰到了就把那一两个话题的几条拼成一段,接在项目经验后面进执行者的指令,并记一行 `matter_topics`。
- **delegate**(`POST /v1/delegate`):只有主人自己的会话发起的(令牌里的 chat 是主人、档位 admin)才做;同样只用索引,
  简报接在 prompt 后面(和 `context_summary` 同一个位置)。
- **私密的话题(`private`)永远不进简报** —— 执行者 / 被咨询的那一家不该看到主人的情绪、人际关系。
- 简报开头写明「CC 记得的相关背景,可能过时;和任务要求冲突时以任务为准」。

### 做完了:结论写回话题

- **工作台**:一轮真的完成(和 `onTurnCompleted` 同一处)⇒ 读这件事在 `written_back_cursor` 之后的最后那条 agent 回话(T1 同一个切段),
  给每个挂着的话题加一条 `conclusion`(`source='work'`、`matter_id` 指回):line = `<任务标题>:<结论第一行>`,body = 结论(≤ 600 字);
  推进 `written_back_cursor`。失败只记一行,不影响任务收尾。
- **delegate**:回答成功 ⇒ 给碰到的话题加一条 `conclusion`(`source='delegate'`):line = `问 <peer>:<问题第一行>`,body = 回答。
- **不重复**:T1 每天的抽取读 agent 的活时,跳过已经写回过的那几段(结论 cursor ≤ `written_back_cursor`)。
- 没挂上话题的活照旧由 T1 每天抽取时归到话题里(慢一天,但不丢)。

### 看得见吗

**看得见(轻微)**:执行者的指令里多一段背景,活的做法可能因此不同(这是要的效果:换一家来做,也知道以前定过什么)。
话题里会多出 agent 写回的结论(T4 泡泡里才看得到)。界面不变。

## 后续(整合者 2026-11-05 对四个待定问题的默认答案;主人可以再改)

### ① 换了说法、一个词都不沾:`topic_search` 工具

不每轮叫模型。给主人对话里的主模型一个只读工具 `topic_search(query)`(话题索引 + 条目),提示词加一句:主人说到 CC
对不上号的事(「那个问题」「上次那个」),先搜话题再答。只给 admin 会话;私密话题只有从主人自己的对话里才搜得到。
评测样本:「开视频会议卡顿那个问题后来怎么定的」要调这个工具、搜到 bx。

### ② 敏感细节

- **交给执行者的简报只带索引行,不带细节**(T3 的简报、delegate 的简报都是)。
- 写进话题的那一刻就去掉明显的身份号(`lib/redact-identifiers.ts`):EIN 样子的 `NN-NNNNNNN`、卡 / 账户「尾号 NNNN」、
  `~/.private_keys` 底下和 `.p8` 的密钥文件路径、电话(美国 / 中国手机;真库副本上出现过一个)、令牌(`sk-…`、`ghp_…`、`Bearer …`、JWT …)。条目的 line / body、话题摘要都过一遍。
  存下来的、调进主人对话的、交给执行者的都是去过的那一份 —— 选了「全都去」,比「主人对话里原样、别处去掉」简单,
  也不会因为某条路忘了去而漏出去。

### ③ 私密的关系话题

照旧:只在主人自己的对话里调,永远不进简报、不交给执行者。

### ④ 流水太碎:睡一觉时整理

每晚整理记忆(`features/memory/nightly-runtime.ts`)真跑过一次之后(不是每 15 分钟那一拍「还没到点」),接着整理
**这次以来改过的话题**:一个话题里还算数的条目交给便宜模型,把重复的进展并成一条「现在到哪了」,去掉提交号。
- 存法(v104 里加两列,v104 还没进 dev):`topic_entries.superseded_by` —— 被并掉的旧条目标 `superseded`、指向新的那条,**不删**;
  `thread_extract_state.consolidated_to_ts` —— 整理到哪。
- **只并认得出是同一件事的**(整合者第二轮,2026-11-05:记错比记乱更糟;第一版试跑把 D-U-N-S / Mercury 两步验证 / 8822-B 并成了一条):
  - progress:模型**只分组**,不写文字;代码再核 —— 组里每一条都要和最新那条共享至少 2 个主题词(中文二字词 / 英文词,先去掉话题自己的标题和别名里的词)。
  - fact:不问模型,代码判几乎一样(词的 Jaccard ≥ 0.8)才并。
  - 承诺、决定、结论不并;已经 superseded 的照旧。
- 并出来的那条:**line = 被并的里面最新那条的原话**(去提交号);较旧那几条的 line 原样折进细节(「之前:」)。不是模型改写。
- **话题摘要不让模型写**(第一版试跑模型把「待邮寄」写成了「已寄出」):摘要 =「它是什么」+「现状:」+ 最新的那一行状态
  (最新的进展 / 结论,没有就最新的决定;≤ 80 字,在分句处切)。「它是什么」存在 `threads.description`(v104),**只在抽取时写**,
  睡一觉的整理不碰它;老话题迁移时先填成老摘要。
- 剩下还算数的条目,提交号按规则去掉(`commit 3897195`、`(e2aa78ba)`)。
- 便宜模型失败:同一个话题重试一次;还不行这个话题跳过,水位不前移,下一晚再来。网络不安全 ⇒ 整批停。
- 条目少(≤ 3 条还算数)或进展不到两条的话题不叫模型。


## 2026-11-08 修订:项目近况排除机器例行流水

- 只记主人在这个项目上的决定、结论、进展与承诺,以及以后用得上的事实和配置。CLI 自动升级、自检、self deploy、soak、迁移版本号不是项目进展。主人开发这些能力的决定、修复、欠项和桌宠演示成果照常记。
- 自动升级、开机和重启通知保留 `messages.source=speech:<kind>`,微信与 App 退路一致。待说队列把例行通知与主人事项回报分开发,避免按一个 kind 丢掉混合正文。新增消息和历史尾部在进抽取模型前排除例行来源,水位照样越过它们。
- T3 直接写回与 T1 共用自检 / 草稿来源排除。旧记录缺来源时,只识别整条都是升级等回执的文本;混合记录保留。召回索引、模型候选、摘要与 consolidate 输入均排除识别出的旧噪声,历史条目状态留给显式清理命令处理。
- 排序:明确查询相关度和模型点名优先;同等相关按承诺 → 明确未完成的进展 → 决定 → 结论 → 一般进展 → 事实,再按新近。`live` 表示条目仍算数,不表示工作尚未完成;暂不加字段,仅把带「尚未 / 待 / 欠 / 阻塞」等明确措辞的 progress 提前。终端开场没有查询,直接用同一优先级,最多 6 条。

### 一次性、可回滚的清理

`wechat-cc dialogue cleanup-topic-noise --db <现有 SQLite 文件> --chat-id <主人 chat>` 默认只读预览,不使用默认生产路径、不执行迁移、不调用 daemon 或模型。整合者审阅候选后加 `--apply --journal <新文件>`,按现有「不对」语义标 `superseded`、`superseded_by=NULL`,不删记录;从保留条目重建受影响摘要,无可用状态时退回 description。

应用前以 0600 独占创建并落盘完整前后快照;同一 SQLite immediate 事务内核对话题和全部条目,再整批更新。`--rollback --journal <文件>` 只在数据库路径 / 文件身份、chat 和全部相关内容仍等于 after 快照时恢复 before;后来的修改、新条目或纠正会阻止回滚。已有取代链、原文、来源和事项关联均保留。回滚正常产生投影版本变更,不倒退订阅修订计数。
