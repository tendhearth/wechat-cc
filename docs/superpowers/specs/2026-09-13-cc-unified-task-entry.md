# CC 统一任务入口：持续交付与验收

用户目标：日常执行任务只需打开 CC，由 CC 管理 Claude、Codex 和其他合适的 agent / LLM；微信也是同一后台的入口。保持陪伴与工作的边界，减少转述、重复配置和丢失上下文。用户已授权持续推进，不逐步请求确认。

本文件延续 `2026-09-12-cc-task-entry-scope.md` 的两栏工作台和已实现的任务模型，扩大后续能力验收，不把已有三段任务循环等同于整个目标完成。

## 实现原则

- 参考 Paseo 的后台持有会话、多客户端接入，Orca 的项目隔离与成果检查，Codex 的原生会话 / turn / item 协议。引用或借用前核对主仓库的实现，不按名称推断 DeepSeek harness 的身份。
- 用户只看到任务、执行者、结果和需要处理的事项；扩展功能仍按需展开，不新增常驻流程图、终端墙或设置表单。
- 各通道调用同一任务服务。微信的普通聊天不自动变成当前任务输入，也不使用全局“最后一个任务”来猜路由。
- 显示“已传达”须有执行器确认。排队消息显示“下一轮”，失败或停止后未交付的内容可找回。
- 保留任务、执行轮次、请求和成果版本身份。过期 / 错任务 / 错所有者 / 重复授权不得作用于另一请求。
- 恢复原生项目能力不等于恢复 CC 伴随服务的全局权限。不得继承 companion prompt、微信发送 / 私人记忆凭证或 daemon bypass。
- 不能用测试桩证明真实 harness 支持。协议 / 服务测试后，使用隔离目录、自己创建的规则和工具做真实验收，不操作用户未知的 MCP 服务或发送真实微信消息。

## 本轮交付检查

1. 核对原生配置继承的精确边界，按受支持接口修复可落地的能力，并把尚未支持的部分如实记录。
2. 微信任务控制沿用同一任务服务，补齐运行中输入和待处理事项；覆盖通道所有权、跨任务与重复处理。
3. 定向测试、完整类型检查、原生隔离验证与独立代码审查。每个可独立验证的变化单独提交；不自动推送、不替换用户正在运行的正式 bot。

本轮完成不表示总目标完成。上表中未验证项继续保留，后续以用户仍需离开 CC 的具体原因决定优先顺序。
