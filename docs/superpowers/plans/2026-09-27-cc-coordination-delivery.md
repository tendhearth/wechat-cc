# CC 用户交办与 agent 协作：后续交付计划

> **For agentic workers:** 执行已批准的产品实现计划时使用superpowers:subagent-driven-development或superpowers:executing-plans。本文确定交付顺序、选型规则与验收门槛，不替代协作功能的详细接口设计。所有未执行项保持未勾选。

**Goal:** 用户在CC交代目标和材料，CC通过已有执行能力让Claude/Codex分工、回传、审查，用户只需跟进结果与处理待决事项。

**Architecture:** 优先复用CC的委派工具、workbench任务生命周期与成果记录，补适合agent使用的窄权限控制入口及协作流程。以Paseo已发布的编排工具和技能为对照，以Orca任务依赖/交接实现为参考；外接Paseo作为比较选项，临时JSON交接不作为产品前置。

**Tech Stack:** 现有TypeScript、Bun/Node、workbench内部API、CLI/MCP接入与原有SQLite存储；本计划不引入新依赖、表或运行服务。

**Spec:** 已有[第一批设计](../specs/2026-09-26-task-entry.md)与[实施计划](2026-09-26-task-entry.md)；协作方向依据[调研与固定源码证据](../reports/2026-09-27-agent-coordination-research.md)，协作生产契约在阶段B收敛。

## Global Constraints

- 本方只使用codex/cc-task-entry及已分配工作区；各自推自己的分支、开PR，ggshr9串行合dev、部署及发布。已约定范围见[分工说明](2026-09-26-cc-agent-coordination.md)。
- 第一批用户交办继续先行；不把协作工具、记忆纠正、设备token改造同时塞入这批改动。
- 对方⑥⑦等待第一批合入；协调生产接线以相关接口/鉴权/拆分边界稳定并明确范围为门槛，不机械等待无关重构。
- 产品设计只要求用户使用CC；provider选择、任务ID和编排工具属于内部实现，详情按需查看。
- 不把扫描到的外部会话视为已纳管，不并发恢复同一活动原生session；历史导入与接管原进程分开验收。
- 不把admin/operator凭据直接交给任意agent，不把其他agent的消息当主人批准。

## Review Focus

- 创建重试和回包丢失：同一请求只对应一个任务和一次派工，不偷偷产生第二个worker。
- 追加与迟到事件：taskId稳定，runId与requestId准确，旧回合消息不能误投下一轮。
- 权限范围：只操作允许的任务/动作；路由白名单不等于任务归属检查，过期提问与批准不能跨轮使用。
- 等待与审查：本轮答复不等于会话关闭；审查引用确定的成果版本/hash、分支和提交。
- 中断与冲突：离线、服务重启、provider不可用、同目录占用时显示真实状态；合并依赖只能由已核验的仓库事件解除。

## 阶段A：交付已有第一批，先让普通用户的一件事走通

- [ ] 按既有计划Task0复核基线、守卫、迁移末条和独立测试环境。保留既有失败证据，后续迁移按实际基线追加。
- [ ] 执行Task1–4：持久创建登记、独立事项目录、统一入口与授权接线。遵守现有第一批完整接口契约，不再扩写另一份。
- [ ] 执行Task5–9：桌面交办、手机文字/材料上传、同一事项续说和回执恢复。文字可先验证，文字与材料均通过才交付整批。
- [ ] 执行Task10：桌面→手机→桌面同一task/matter，真实图片被执行者读到，成果可打开并继续修改；交付PR与验证证据，真机未验项明确保留。

产物：第一批实现PR及其验收记录。已有详细文件/测试清单在[实施计划](2026-09-26-task-entry.md)，当前没有完成项。

## 阶段B：并行准备协作设计，先验证复用范围

- [ ] 形成一页能力映射：创建、发送/续接、等待、读取结果、取消，逐项对应Paseo工具、CC已有接口和真正缺口。代码落点为src/mcp-servers/delegate/main.ts、src/daemon/bootstrap/delegate.ts、src/daemon/internal-api/routes-workbench.ts及route-tiers/token-registry。
- [ ] 设计同一条隔离验证流程：Claude整理要求→Codex在独立目录完成小改动→给同一任务追加要求→固定成果→Claude在新上下文审查→返回主事项。普通用户始终从CC进入。
- [ ] 在独立测试数据与目录中验证CC现有链路。首次试验可用已有授权测试客户端，不把试验凭据方案直接带进产品。以真实任务/回合/成果身份记录结果，禁止把mock通过写为真实执行者通过。
- [ ] 决定复用方案：已有运行时可完成链路时采用“CC任务接口＋窄权限CLI/MCP＋协作流程”；若出现明确能力缺口，才针对该缺口比较Paseo CLI/SDK。外接方案必须说明额外daemon、身份、成果和恢复的所有权，不能只看demo能跑。

产物：可复核的能力差异、运行验证记录、单一选型结论和协作设计。此阶段的准备不占用对方待改模块；本轮只制定验证计划，尚未启动试验。

## 阶段C：交换新基线与接口边界

- [ ] 第一批经主人合入后，核验GitHub上的目标仓库、PR、目标分支和合并提交，区分合并提交与随后变化的dev头，再形成交接材料。
- [ ] 对方⑥设备权限与⑦大模块拆分按已约定顺序推进。本方只读评审其契约，避免同时改settings-panel、service、bootstrap、cli及迁移。
- [ ] 协作实现前明确哪些接口已稳定、哪个提交作为基线、剩余热点由谁负责。原生任务入口和授权若仍在变化，先完成设计/测试准备，生产接线串行合入。

产物：包含已核验提交与范围的交接说明。合并、部署和批准仍由主人执行。

## 阶段D：交付最小产品协作链

- [ ] 根据阶段B选型和阶段C基线，将权限、任务/回合身份、接口错误与恢复语义写成详细设计及逐任务实施计划；实现前接受独立审查，不凭本排期文档直接新增接口。
- [ ] 优先复用已有任务记录与路由，补统一控制入口。新CLI业务位于src/cli/<group>.ts，遵守cli-ratchet；MCP入口只暴露实际需要的动作，所有新增暴露面按真实调用路径登记。
- [ ] 固定首个协作流程为“分派实现→追问/补充→取得确定成果→独立审查→回到CC汇报”。通过后再扩到多个并行worker；编辑者分别使用独立工作区。
- [ ] 验收Review Focus的五组情况：重复派工、旧run误投、越权任务操作、审查对象漂移、中断后状态误报均须有行为测试和必要实机证据。
- [ ] UI在原事项中显示正在处理、正在复核、需要你决定及最终成果；更细的执行者活动按需展开。agent间无需用户复制说明，不承诺自动合并发布。

产物：独立协作功能PR及验收记录。通用成员中心、完整邮箱产品、文件预约系统和协议联邦不作为这一批前置；只有验收暴露真实缺口时才增补。
