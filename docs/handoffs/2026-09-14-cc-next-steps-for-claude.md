### 2. 做一次“我今天只打开 CC”的实际试用

**要解决：** 功能表很完整，但人在干活时仍频繁退回原工具。

- [ ] Claude 和 Codex 各做一项真实的小任务，包含读材料、执行工具、查看成果和继续修改；使用隔离样例项目，不让测试修改主人的工作。
- [ ] 补充要求、上传材料、处理权限/提问、取消、重开窗口、继续原会话都实际走一遍；有子助手或后台命令时，继续观察主回复之后的状态。
- [ ] 两个项目同时运行，再试同项目两项工作；检查输入、权限、停止和结果归属，以及排队是否说得清楚。
- [ ] 从已存在的 Claude/Codex 历史继续一件事，核对目录、执行者、会话身份、项目规则与工具配置。区分“继续已保存会话”和“接管别处正在运行的进程”。

**完成标准：** 产出一张很短的真实阻碍清单，优先修影响完成任务的前三项。已有功能好用就保留，不凭想象重构整个工作台。界面尽量仍是两栏，细节按需展开。

## 第二批：由真实需求决定的扩展

### 4. 微信真正成为离开电脑后的入口

- [ ] 补真实账号验收：创建/补充任务、待决请求、完成通知、正文分页和索取成果；真实发送前取得主人的明确安排，不把开发测试发给联系人。
- [ ] 关注手感：编号是否太长、错误能否恢复、电脑离线时是否说清楚、通知是否恰到好处。
- [ ] 对比引用回复、快捷操作等方式能否减少手输，但保持明确任务归属。不能凭“最近一个任务”猜用户在指谁。
- [ ] 测重复点击、过期审批、多个任务等待、连接中断；未经确认的发送不能自动重复。

完成标准：离开电脑后能处理常见阻塞并拿到正确版本的成果；无法在手机完整判断的内容明确回桌面。

### 5. API 模型要有明确、实用的工作范围

- [ ] 用实际兼容端点完成“读材料 → 请求权限 → 产出文件 → 再修改要求 → 继续”的任务，加入取消与失败；短句聊天成功不代表此流程成功。
- [ ] 选一个真实办公需求，例如比较资料或整理清单，评价是否值得从 Claude/Codex 切给 API；记录效果、时延和可取得的用量证据，不臆测成本。
- [ ] 核对不支持工具/图片的模型在选择前如何解释；连接、模型、接入方式不要再次混成一张难懂的名单。
- [ ] 若真实需求被 PDF/Office 或成果类型挡住，先选一个高频缺口做透。不要为了“多模型”立刻给 API 加一套万能 shell/MCP。

完成标准：至少有一类用户任务能稳定交给 API 做，能力边界和错误可理解。真实费用、密钥、外部服务使用依照主人授权安排。

### 6. 新用户接入与长期使用

- [ ] 在干净用户环境试一次：能否发现已装/已登录的 Claude/Codex，选项目后开始做事，遇到没装、没登录、额度不足或不兼容版本能否自己恢复。
- [ ] 区分“已有配置”和“验证可用”，避免注册成功就显示可执行。
- [ ] 试上百条旧任务后的搜索、归档、重新接续、磁盘占用和成果找回。清理策略要能说明影响，不自动抹掉用户工作。

完成标准：新用户不必理解 provider/CLI/harness 就能开始；老用户能找回一件上周做的事。

### 7. 更多执行者与多设备：先证明需求，再决定形态

- [ ] Cursor/agy 或其他执行者：按当前官方接口重新评估权限、配置、停止、恢复和事件完整性。之前没接入不等于永久不可行；也不能为多一个选项默默放宽承诺。
- [ ] 跨设备先分清：手机看同一后台、远程电脑执行、把任务迁到另一主机，是三件事。选一个真实场景验证，不一口气做同步/云端平台。
- [ ] 若能提供清楚的受限模式，可以讨论；让用户知道具体限制，不伪装成同等接管。

完成标准：先给选择依据与小范围验证，再决定做不做。模型数量本身不是成功指标。
